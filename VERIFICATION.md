# How Emetgate Is Verified

Generated by `tools/verification_page.py` from `tests/mutations.json` and `README.md`. Do not edit by hand; `python tools/verification_page.py` regenerates it, and `python tools/verification_page.py --check` fails if this file is out of date.

The claim this page backs: the kernel's guards are not just written, they are each covered by a test that fails when the guard is weakened one way, and checked as far as the mutation tool could push it when the guard survives unchanged. This follows the framing in Anderson's reference monitor: complete mediation is `emetgate lockdown`, tamper-resistance is the sandbox and the ledger's trust rules, verifiability is this page.

## What this system does not prove

- **Semantic correctness.** A change that parses, stays in its structural bounds and passes the given tests can still do the wrong thing; whether it does is undecidable in general (Rice's theorem) and this kernel does not try to decide it. It replaces search-and-replace editing with a checked one, not a proof of intent.
- **The test oracle's own strength.** For an unbounded (test-gated) change, the verdict is only as good as the test command the user supplied; a weak or missing test lets a wrong change through the same way it would without this kernel.
- **Anything outside the gate.** These guarantees hold for edits that go through `try`/`try_batch`; a tool or a human editing the file directly bypasses all of it, which is why `lockdown` exists and is a separate claim from the ones on this page.
- **Non-Windows platforms.** The sandbox depends on Windows Job Objects and restricted tokens; none of the sandbox mutation or red-team results say anything about another OS.
- **A mutant proven equivalent or open stays open.** "Equivalent" here means a specific argument was made for why no test can distinguish the mutant from the original, not a machine-checked proof; "open" means no killing input was found yet, not that none exists.
